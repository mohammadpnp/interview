‏پاسخ‌های کامل سوالات Laravel Advanced

‏بخش پایه

‏1) queue در Laravel چه زمانی لازم می‌شود؟
‏پاسخ:
‏- برای کارهای زمان‌بر که نباید latency API را بالا ببرند.
‏- ارسال ایمیل/نوتیفیکیشن، پردازش فایل، callهای خارجی.
‏- resilience بهتر با retry مستقل.
‏- trade-off: پیچیدگی async و consistency.

‏2) event و listener چه تفاوتی با service call مستقیم دارند؟
‏پاسخ:
‏- call مستقیم coupling بالا و اجرای همزمان دارد.
‏- event/listener decouple ایجاد می‌کند و subscriberهای متعدد ممکن می‌شود.
‏- برای side effectهای غیرcritical مناسب‌تر است.
‏- tracing و debugging در event-driven پیچیده‌تر می‌شود.

‏3) policy را کجا تعریف می‌کنی؟
‏پاسخ:
‏- در لایه authorization (Policies/Gates) مرتبط با resource.
‏- controller/service قبل action حساس از policy استفاده می‌کنند.
‏- ruleها متمرکز و تست‌پذیر می‌شوند.
‏- منطق authz نباید پراکنده در controllerها باشد.

‏بخش متوسط

‏1) چگونه retry job را امن طراحی می‌کنی؟
‏پاسخ:
‏- فقط خطاهای transient را retry می‌کنم.
‏- backoff نمایی + jitter + max attempts.
‏- idempotency key برای جلوگیری از اثر تکراری.
‏- بعد از سقف retry، DLQ/failed jobs triage می‌شود.

‏2) job failure handling را چگونه انجام می‌دهی؟
‏پاسخ:
‏- ثبت دقیق context خطا (payload, attempt, trace).
‏- دسته‌بندی خطای دائمی/موقت.
‏- alert برای failure rate غیرعادی.
‏- ابزار replay کنترل‌شده بعد از fix.

‏3) چه زمانی dispatch after response مفید است؟
‏پاسخ:
‏- وقتی کار ضروری برای پاسخ کاربر نیست ولی باید سریع شروع شود.
‏- کاهش perceived latency کاربر.
‏- برای کارهای mission-critical بهتر است queue پایدار استفاده شود.
‏- process crash قبل اجرا باید در نظر گرفته شود.

‏4) چگونه از اجرای دوباره job حساس جلوگیری می‌کنی؟
‏پاسخ:
‏- idempotency key و unique constraint.
‏- optimistic/pessimistic lock روی resource.
‏- state machine واضح (pending/processed).
‏- dedup log برای audit و debugging.

‏بخش پیشرفته

‏1) یک معماری async برای سفارش/پرداخت طراحی کن.
‏پاسخ:
‏- order service درخواست را ثبت و outbox event تولید می‌کند.
‏- payment consumer رویداد را پردازش و نتیجه را event می‌کند.
‏- order status با eventهای پرداخت به‌روزرسانی می‌شود.
‏- compensation برای failure و timeout لازم است.

‏2) چگونه consistency بین DB و queue را حفظ می‌کنی؟
‏پاسخ:
‏- outbox pattern در transaction محلی.
‏- publisher قابل‌اعتماد با retry idempotent.
‏- consumer idempotent + inbox/checkpoint.
‏- reconciliation job دوره‌ای برای drift.

‏3) برای queue backlog شدید چه strategy داری؟
‏پاسخ:
‏- scale worker، اولویت‌بندی صف‌ها، throttling producer.
‏- بهینه‌سازی handler (batching, حذف I/O غیرضروری).
‏- جداکردن high-priority queue.
‏- alert بر اساس lag و age پیام.

‏4) چه زمانی event-driven به پیچیدگی غیرضروری تبدیل می‌شود؟
‏پاسخ:
‏- وقتی domain ساده است و latency فوری لازم است.
‏- وقتی تیم ابزار/فرآیند observability و operability ندارد.
‏- وقتی consistency قوی در هر گام حیاتی است.
‏- در این حالت synchronous ساده‌تر و قابل‌اعتمادتر است.
