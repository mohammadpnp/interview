پاسخ‌های کامل سوالات Low-Latency + Realtime Patterns (PHP)

بخش پایه

1) realtime update را در Laravel چگونه پیاده می‌کنی؟
پاسخ:
- event broadcasting با queue-backed worker.
- websocket gateway (داخلی یا سرویس جانبی) برای push.
- کانال‌بندی دسترسی و auth روی channel.
- fallback polling محدود برای client ناسازگار.

2) چرا queue در نوتیفیکیشن لحظه‌ای مهم است؟
پاسخ:
- spike پیام را جذب می‌کند و API را سبک نگه می‌دارد.
- retry مستقل در خطاهای موقت.
- decouple producer از delivery mechanism.
- نیاز به monitoring lag و failure دارد.

3) WebSocket چه مزیتی نسبت به polling دارد؟
پاسخ:
- کاهش latency و هزینه requestهای تکراری.
- push واقعی از سرور به کلاینت.
- در scale مناسب‌تر برای آپدیت مداوم.
- مدیریت connection state پیچیده‌تر است.

بخش متوسط

1) bottleneck realtime pipeline را چگونه پیدا می‌کنی؟
پاسخ:
- اندازه‌گیری end-to-end latency از event تا دریافت client.
- تفکیک queue lag، processing time، gateway dispatch.
- tracing/correlation id برای هر پیام.
- سپس بهینه‌سازی گلوگاه غالب.

2) چه زمانی نیاز به سرویس جانبی Go/Node برای realtime داری؟
پاسخ:
- connection همزمان بالا و latency سخت‌گیرانه.
- workload realtime غالب بر web requestهای معمول.
- نیاز به memory/concurrency profile متفاوت.
- وقتی migration cost از benefit کمتر باشد.

3) چگونه latency endpointهای critical را کاهش می‌دهی؟
پاسخ:
- cache hot data و کاهش I/O زنجیره‌ای.
- query/index optimization و pooling صحیح.
- async کردن side-effect غیرضروری.
- timeout دقیق و fail-fast روی dependency.

4) backpressure در سیستم event-driven چه شکلی پیاده می‌شود؟
پاسخ:
- queue bounded و محدودیت consumer concurrency.
- drop/defer policy برای پیام کم‌اهمیت.
- throttle producer در saturation.
- alert روی lag/age message.

بخش پیشرفته

1) معماری realtime پایدار برای 1M کاربر آنلاین طراحی کن.
پاسخ:
- لایه gateway افقی مقیاس‌پذیر با shard بر اساس channel/user.
- message broker برای fan-out کنترل‌شده.
- state lightweight و externalized در صورت نیاز.
- observability کامل + auto-scale + multi-region strategy.

2) اگر بخشی از جریان realtime fail شد، recovery چطور انجام می‌شود؟
پاسخ:
- detect سریع failure stage.
- replay از queue/log با idempotent consumer.
- fallback موقت (polling/degraded mode).
- RCA و hardening برای جلوگیری از تکرار.

3) strategy failover برای websocket gateway چیست؟
پاسخ:
- چند replica با load balancing و health check.
- session re-establish سریع سمت client.
- sticky strategy فقط در صورت نیاز.
- runbook failover و تست دوره‌ای chaos/drill.

4) چگونه consistency بین realtime event و state دیتابیس حفظ می‌شود؟
پاسخ:
- event publication بعد از commit دیتابیس (outbox).
- versioning/sequence برای رد پیام قدیمی.
- reconcile job برای drift.
- UI باید eventual consistency را به‌صورت قابل‌فهم مدیریت کند.
