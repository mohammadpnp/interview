پاسخ‌های کامل سوالات Database (PHP Track)

بخش پایه

1) تفاوت MySQL و PostgreSQL در پروژه‌های شما چه بوده؟
پاسخ:
- PostgreSQL برای query پیچیده، type system قوی و امکانات advanced بسیار خوب است.
- MySQL برای workloadهای رایج وب mature و ساده عملیاتی است.
- انتخاب وابسته به نیاز domain، مهارت تیم و ecosystem است.
- هر دو با index و query صحیح می‌توانند performant باشند.

2) primary key و unique key چه تفاوتی دارند؟
پاسخ:
- primary key شناسه اصلی جدول است و null نمی‌پذیرد.
- unique key یکتایی را روی ستون/ترکیب دیگر enforce می‌کند.
- هر جدول یک PK دارد ولی چند unique ممکن است.
- در business ruleها unique constraint بسیار حیاتی است.

3) Redis را کجا استفاده کرده‌ای؟
پاسخ:
- cache read-heavy endpointها.
- session store، rate limit، queue backend.
- lock کوتاه‌مدت یا distributed counter.
- نه به‌عنوان source of truth تراکنشی اصلی.

بخش متوسط

1) چگونه query کند را تشخیص می‌دهی؟
پاسخ:
- slow query log/APM و endpoint latency correlation.
- plan تحلیل با EXPLAIN.
- index usage، row scanned، sort/hash هزینه‌بر.
- سپس اصلاح query/schema و benchmark قبل/بعد.

2) deadlock چگونه رخ می‌دهد و چطور حل می‌شود؟
پاسخ:
- دو transaction lock متقابل روی منابع متفاوت می‌گیرند.
- lock ordering ناهماهنگ علت رایج است.
- کاهش طول transaction، ordering ثابت lock، retry کنترل‌شده.
- مانیتور deadlock rate برای تشخیص الگوی تکراری.

3) strategy شما برای cache invalidation چیست؟
پاسخ:
- TTL پایه + invalidation event-based روی write حساس.
- key naming استاندارد و قابل‌ردیابی.
- cache stampede control با jitter/single-flight.
- consistency نیازمند تعریف freshness SLA است.

4) چه زمانی denormalization منطقی است؟
پاسخ:
- وقتی read-heavy است و joinهای سنگین bottleneck شده‌اند.
- وقتی تاخیر eventual consistency قابل‌قبول است.
- باید فرآیند sync/rebuild واضح داشته باشد.
- بی‌ضابطه denormalization maintenance را سخت می‌کند.

بخش پیشرفته

1) migration بدون downtime چطور انجام می‌دهی؟
پاسخ:
- expand-contract: افزودن column/index سازگار.
- deploy اپ سازگار با هر دو schema.
- backfill تدریجی و monitor.
- پس از اطمینان، cleanup مرحله آخر.

2) چگونه data consistency در workflow مالی حفظ می‌شود؟
پاسخ:
- unique/idempotency، transaction کوتاه و دقیق.
- state machine و audit trail غیرقابل‌انکار.
- outbox/event برای sync بین سرویس‌ها.
- reconciliation دوره‌ای و alert mismatch.

3) برای dataset بزرگ چه partition/sharding strategy داری؟
پاسخ:
- partition بر اساس time/tenant وقتی access pattern واضح است.
- sharding وقتی scale یک نود کافی نیست.
- routing key باید پایدار و متوازن باشد.
- complexity عملیاتی بالا می‌رود؛ observability الزامی است.

4) چه زمانی read replica ارزش عملی دارد؟
پاسخ:
- read-heavy endpointهای غیرحساس به lag.
- جداکردن analytic/reporting از primary.
- باید replica lag monitor شود.
- جایگزین optimization query/index نیست، مکمل آن است.
