‏پاسخ‌های کامل سوالات Microservices + gRPC

‏بخش پایه

‏1) gRPC چه مزایایی نسبت به REST دارد؟
‏پاسخ:
‏- قرارداد قوی با Proto و تولید کد client/server.
‏- payload باینری کوچک‌تر و latency کمتر نسبت به JSON در بسیاری از سناریوها.
‏- پشتیبانی built-in از streaming.
‏- مناسب‌تر برای ارتباط داخلی سرویس‌ها؛ REST برای public API هنوز رایج‌تر است.

‏2) تفاوت unary و streaming RPC چیست؟
‏پاسخ:
‏- unary: یک request و یک response.
‏- server/client/bidi streaming: جریان پیام‌ها بین دو طرف.
‏- streaming برای realtime/feed/long-running task مناسب است.
‏- مدیریت backpressure و timeout در streaming حیاتی است.

‏3) deadline در gRPC چه کاربردی دارد؟
‏پاسخ:
‏- سقف زمان انتظار call را مشخص می‌کند.
‏- از اشغال resource و hanging request جلوگیری می‌کند.
‏- در chain سرویس‌ها باید deadline propagation انجام شود.
‏- بدون deadline، خطای dependency می‌تواند کل سیستم را degrade کند.

‏بخش متوسط

‏1) backward compatibility در Protobuf را چگونه حفظ می‌کنی؟
‏پاسخ:
‏- field number تغییر نده، field حذف‌شده را reserve کن.
‏- optional field جدید اضافه کن و default امن بده.
‏- تغییر معنای فیلد موجود ممنوع؛ باید فیلد جدید بسازی.
‏- contract review و versioning policy تیمی لازم است.

‏2) چگونه idempotency را در endpointهای حساس پیاده می‌کنی؟
‏پاسخ:
‏- کلاینت idempotency key می‌فرستد.
‏- سرور نتیجه request با آن key را در بازه زمانی ذخیره می‌کند.
‏- درخواست تکراری همان پاسخ قبلی می‌گیرد، نه اجرای دوباره عملیات.
‏- در عملیات مالی/سفارش این کار برای جلوگیری از duplicate حیاتی است.

‏3) چه زمان synchronous call بد است و باید async/event استفاده کرد؟
‏پاسخ:
‏- وقتی کار طولانی یا غیرضروری برای پاسخ فوری است.
‏- وقتی وابستگی‌های متعدد احتمال cascading failure را بالا می‌برند.
‏- وقتی نیاز به decouple و retry مستقل داری.
‏- event-driven latency نهایی را بالا می‌برد ولی پایداری و مقیاس‌پذیری را بهتر می‌کند.

‏4) چگونه service discovery را طراحی می‌کنی؟
‏پاسخ:
‏- در Kubernetes با DNS/service abstraction ساده و استاندارد است.
‏- خارج از K8s معمولا registry (Consul/etcd) + health check.
‏- client-side یا server-side load balancing بسته به stack.
‏- stale endpoint و health-state lag باید در design دیده شود.

‏بخش پیشرفته

‏1) cascading failure چیست و چگونه مهار می‌شود؟
‏پاسخ:
‏- خرابی یک dependency باعث اشباع thread/connection و خرابی زنجیره‌ای می‌شود.
‏- مهار: timeout کوتاه، circuit breaker، retry محدود با jitter، bulkhead.
‏- fallback یا degraded mode برای قابلیت ادامه سرویس.
‏- alertهای زودهنگام روی saturation/error-rate ضروری است.

‏2) برای یک call chain چندمرحله‌ای چه retry strategy پیشنهاد می‌کنی؟
‏پاسخ:
‏- فقط روی خطاهای transient retry کن، نه خطاهای business/validation.
‏- exponential backoff + jitter برای جلوگیری از retry storm.
‏- سقف retry و deadline کلی request رعایت شود.
‏- idempotency precondition است؛ وگرنه retry می‌تواند داده را خراب کند.

‏3) چگونه distributed tracing را در میکروسرویس‌ها اجرا می‌کنی؟
‏پاسخ:
‏- propagation trace context در header/metadata.
‏- span برای هر عملیات I/O مهم (db, cache, outbound call).
‏- tag کردن خطاها و latency stageها.
‏- اتصال trace به log و metric برای triage سریع.

‏4) API Gateway چه زمانی ارزش دارد و چه زمانی bottleneck می‌شود؟
‏پاسخ:
‏- ارزشمند برای auth مرکزی، rate limit، routing، observability.
‏- bottleneck وقتی همه منطق بیزنسی به gateway نشت کند.
‏- gateway باید thin بماند؛ orchestration پیچیده بهتر است در backend مخصوص باشد.
‏- HA و autoscaling gateway باید جداگانه طراحی شود.
